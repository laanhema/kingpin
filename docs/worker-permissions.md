# Worker permissions

[Back to the README](../README.md).

**What a Claude Code worker may edit.** A worker runs in its own leased worktree with every tool. `worker/hooks.json` adds a `PreToolUse` hook (`kingpin guard hook worker`) for `Edit`, `Write` and `NotebookEdit`: it allows files inside the worker's worktree and its task folder (`~/.kingpin/tasks/<id>/`, where it writes `status`, `question.md` and `report.html`), and denies every other path, including the main checkout. The hook decides before the permission prompt or the auto-mode classifier, so these edits need no human approval. It does not sandbox `Bash`. The worktree it allows is pinned by `KINGPIN_WORKTREE` (set by the launch script) or by `WORKTREE=` in the task's `task.env`, never by the session's working directory, so a worker that `cd`s to the main checkout gains nothing and one that `cd`s to its task folder keeps its worktree. Both hooks fail closed: if `kingpin-guard` cannot run (for example `KINGPIN_ROOT` is unset), or the decision cannot be made (a payload it cannot read, a worker tool call with no file path, a worker with no resolvable worktree, or an orchestrator session whose working directory cannot be resolved to a git worktree), the edit is denied. The orchestrator hook decides on the session's checkout rather than the target, so a path-less call such as `Agent` is still allowed from a linked worktree. It denies in the main checkout of any repository, where `git rev-parse --git-dir` equals `git rev-parse --git-common-dir`, not just in the Kingpin checkout.

**Why workers used to lose `Edit`, `Write` and `Agent` (issue #40).** Claude Code loads the main checkout's `.claude/settings.local.json` for its linked worktrees. The orchestrator guard used to be `permissions.deny` rules for `Edit`, `Write`, `NotebookEdit` and `Agent` in that file, so every worker started without those tools, and fell back to `Bash` heredocs that the auto-mode classifier sometimes denied. A deny rule beats any allow rule, so a worker cannot override it. To reproduce: in a throwaway repo, put those four deny rules in `.claude/settings.local.json` of the main checkout, add a linked worktree with `git worktree add`, and run `claude -p "List your tools"` in the worktree; the four tools are missing, and they come back when the file is moved away. The guard is now a hook that denies only when the session runs in the main checkout of a git repository (where its `git rev-parse --git-dir` equals `--git-common-dir`), or when it cannot resolve the session's directory to a git worktree (fail closed).

**Why a worker never sees the orchestrator contract (issue #96).** The contract used to live in the tracked `AGENTS.md`, which every harness loads, while the file the spawn pointed at was silently ignored: OpenCode reads `opencode.json`, not `.opencode/config.json`, and agy skips a rules file with no `trigger:` frontmatter. A worker could wake up reading only the orchestrator's job description and spend its first turn reporting fleet status. The contract now lives in `orchestrator/contract.md` and is installed only into instruction sources that exist in the main checkout, while `AGENTS.md` describes the repository. Before opening a worker window, `kingpin spawn` runs `kingpin scope check --harness <h> --worktree <wt> --preamble <task>/preamble.md` and refuses to launch, naming the file, when a source the worker would load carries a contract marker. For OpenCode and agy it also refuses when the preamble is not a source the harness loads; Claude Code receives it through `--append-system-prompt-file`, which the check does not verify. A hit in a global instruction file (`~/.config/opencode/AGENTS.md`, `~/.claude/CLAUDE.md`, `~/.gemini/AGENTS.md`) refuses too, naming the file: that file is yours, Kingpin does not edit it, and a worker that may wake up as the orchestrator is not worth a warning. Set `KINGPIN_ALLOW_GLOBAL_CONTRACT=1` when you keep the contract there on purpose. On OpenCode, the spawn merges the preamble into an existing `.opencode/opencode.json` instead of overwriting it, and refuses when the project tracks that file, because an edit to a tracked config could be committed by the worker. A JSONC config (comments) is read with its comments stripped; `kingpin guard install` refuses to rewrite one, so the main checkout's `.opencode/opencode.json` must be plain JSON. To see what a harness really loads, run `kingpin scope files --harness opencode --worktree <dir>`; it prints one `<kind>\t<path>` line per source (`discovery`, `configured`, `ignored`, `global`).

**Pi.** A Pi worker runs in the same leased worktree and task folder, and `worker/pi/kingpin-harness.ts` answers Pi's `project_trust` prompt yes for that worktree only, comparing resolved realpaths. A worktree that carries the project's own `.pi/` or `.agents/skills` therefore starts unattended instead of stalling on "Trust project folder?". That is the same exposure an agy or OpenCode workspace trust already grants: the project's own extensions and settings execute. There is no Pi path guard (the `tool_call` payload was not measured, so no field name is guessed) and no subagent tool: a delegating skill's steps run inline in the worker. Pi also loads `AGENTS.override.md`/`AGENTS.md`/`CLAUDE.md` from the worktree and its parents, which is why `kingpin scope check --harness pi` names those files before a spawn; the worker's preamble arrives separately through `--append-system-prompt`. The same check walks every `SKILL.md` Pi discovers, because a skill's name and description reach the system prompt before the model asks for it: a project's `.agents/skills` and `.pi/skills` count as `configured` sources, and the user-level directories Pi scans count as `global` (the bridged skills directory `KINGPIN_SKILLS_DIR`, `~/.agents/skills/`, and `<PI_CODING_AGENT_DIR>/skills/`), so a contract carried in a skill refuses the spawn instead of riding the extension's automatic trust answer into the worker. `kingpin scope doctor --harness pi` reports the binary, credentials, skills directory and extension in one command.

**Unblocking a worker.**
- *No `Edit`/`Write`/`Agent` tool:* run `kingpin guard check` in the main checkout. If it reports stale deny rules, run `kingpin guard install` (it removes them) and respawn the worker; a running session keeps the tool list it started with.
- *A `Bash` command denied as "dangerous":* the worker stops with `needs-input`. Approve the command in the worker's tmux window, or add a Bash permission rule with `/permissions`. Workers should edit with `Edit`/`Write`, which the hook allows.
- *An edit denied for being outside the worktree:* the path belongs to the main checkout or another place. Put that change in a task of its own.

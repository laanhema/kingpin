# Multi-Harness Architecture

[Back to the README](../README.md).

Each supported harness uses native configuration and hook mechanisms without dirtying repository tracking:

- **Claude Code**: Workspace trust in `~/.claude.json`. System prompt via `--append-system-prompt-file`. Turn end via `worker/hooks.json`, whose Stop command runs `bin/kingpin-stop`.
- **Antigravity CLI**: Workspace trust in `~/.gemini/antigravity-cli/settings.json`. Rules in `.agents/rules/kingpin.md`, which needs a `trigger: always_on` frontmatter: agy skips a rules file without one, without a word. Turn end via `.agents/hooks.json`, whose Stop command runs `bin/kingpin-stop`.
- **OpenCode**: Autonomous permissions via `--auto`. Instructions in `.opencode/opencode.json`: OpenCode reads `opencode.json` or `.opencode/opencode.json`. Turn end via `.opencode/plugins/kingpin-stop.js`, which calls `bin/kingpin-stop`.
- **Pi**: No worktree file and no trust prompt. The preamble arrives through `--append-system-prompt <task>/preamble.md`, and `-e <checkout>/worker/pi/kingpin-harness.ts` loads the extension from the checkout by absolute path. On `resources_discover` it bridges `KINGPIN_SKILLS_DIR` (default `~/.claude/skills`), so the fleet's `/skill:<name>` commands resolve; on `project_trust` it answers yes for the leased worktree only (resolved realpaths) and never remembers the answer; on `agent_settled` it runs `bin/kingpin-stop`, the same Stop hook the other three use. Pi has no subagent tool, so a delegating skill's steps run inline in the worker.
- **Codex**: The preamble arrives through `-c model_instructions_file <task>/preamble.md`, so the tracked `AGENTS.md` is never rewritten and the worktree holds no preamble file. Codex 0.166 has no slash command for the fleet's skills, so each one is linked into `<worktree>/.codex/skills/<name>` and sent as `$<name>`; a project's own skill at that name is left in place and named. The Linux sandbox is the containment mechanism: `-s workspace-write` with the worktree writable, the task folder (`~/.kingpin/tasks/<id>`, where `status`, `stopped` and `question.md` live) and the worktree's git dir and common git dir as extra writable roots, `/tmp` denied, and `TMPDIR` moved inside the task folder so a suite's `mktemp -d` still works. The two git roots are what lets a linked worktree stage and commit at all, since its index and refs live outside the worktree; the shared common dir is therefore writable by every worker, including the main checkout's `.git/config` and `.git/hooks/`, which `docs/worker-permissions.md` states as the price of the shared object store. Network stays on (`sandbox_workspace_write.network_access=true`), because the fleet's job is `gh` and `git push`; the filesystem confinement is unchanged by that. `-a never` removes the per-command approval prompt, and Codex's separate "Hooks need review" dialog, which `-a never` does not answer, is skipped with `--dangerously-bypass-hook-trust` only when the host really has a hook set (`[features] hooks = true` or a non-empty `$CODEX_HOME/hooks.json`). Turn end is the `notify` program `<task>/notify.sh`, which runs `bin/kingpin-stop`; Codex also fires it for its background title-generation turn, and the hook is idempotent per state. Codex asks before it trusts a folder, and a `-c` override does not suppress that dialog, so a spawn seeds `[projects."<worktree>"] trust_level = "trusted"` in the user's own `$CODEX_HOME/config.toml` (`lib/codex-trust.mjs`) and `kingpin done` (or a failed spawn's cleanup) removes only what that spawn wrote, leaving the user's other keys and entries byte-identical.
- **The orchestrator contract** (issue #96): tracked as `orchestrator/contract.md` and installed only in the main checkout, into `~/.kingpin/orchestrator.md`, `.claude/rules/kingpin-orchestrator.md` and `.agents/rules/kingpin.md`, with `.opencode/opencode.json` pointing at `~/.kingpin/orchestrator.md`. A spawned worker gets `worker/preamble.md` and none of these files.

`bin/kingpin-scope` (`kingpin scope files`) lists the instruction files a harness really loads for a worktree, and `kingpin scope check` exits 1 naming the file when one of them carries the contract; `kingpin spawn` runs it before it opens a window. `kingpin scope doctor --harness pi` adds the Pi readiness probe: binary, credentials, skills directory and extension; `kingpin scope doctor --harness codex` adds the Codex one: binary, what `codex login status` reports, the config store and the skills directory.

### Vision-capable models

An orchestrator session can attach an image to its own context only when its model accepts image input. A text-only model rejects the request with `image input is not available` (the provider may prefix it with `400`), and that rejection poisons the history: every later request resends the same image, so retrying cannot clear it. The session is unrecoverable at that point. Start a new session and hand it the fleet state (`kingpin brief`, `kingpin list` and the pending task records) instead of resending the turn. The guard that keeps an image out of a text-only request belongs in the harness, not in this repository.

Two kinds of tool can put an image into the context: the browser bridge's `chrome-devtools-axi screenshot <path>`, which writes an image file, and any image generator or editor the harness itself exposes. The screenshot call alone adds nothing to the context; reading the file back into the conversation is the step that attaches the image, so confirm the model accepts image input before either step. The bridge's other reads stay text, so `chrome-devtools-axi snapshot` (the accessibility tree), `console`, `network` and `eval` are safe on a text-only model.

Kingpin pins no orchestrator model, so the choice is the harness's: switch it in that harness's own model control before the first screenshot. Pi uses `/model`, and `README.md` records the one-time `/login` step; Claude Code, OpenCode, agy and Codex each choose a model their own way. The model the contract's image-input rule asks you to confirm is the one the session is running, not the one a worker will run.

### Multiplexer

The harness is unchanged by where the worker's terminal lives: the same preamble, hooks and launch flags run in a tmux window or a Herdr pane, and the harness layer never names the multiplexer. That choice is a separate layer, `lib/mux.sh`: `KINGPIN_MUX=auto` (the default) uses Herdr only when the command itself runs inside a Herdr pane and tmux everywhere else, `tmux` and `herdr` force one, and any other value is refused by name. The task record decides for an existing task (`MUX=herdr`, or no `MUX=` line for tmux), so one fleet can hold both. Herdr panes are addressed by label first, because Herdr renumbers a pane that moves across workspaces, and its `pane read` returns plain text rather than JSON. The fleet's Herdr session is `KINGPIN_HERDR_SESSION` (default `kingpin`) and must already be running: `herdr server` is a foreground process, so nothing in Kingpin starts or supervises it. `kingpin spawn` still creates tmux workers; `docs/cli.md` records what that means for a Herdr-only fleet.

### Fleet skills on Pi: support matrix

Pi has no subagent tool, so a skill that delegates runs its steps inline in the worker and loses the
context isolation a subagent would give it. The skills' own no-subagent branches state that. The
`State` column separates what has actually been run on Pi from what is only expected to work: a row
is `measured` only when a real Pi session ran that skill through a real model, and the evidence names
the command.

Provider and model for every measured row: `openrouter` / `anthropic/claude-sonnet-4.5`, Pi 1.5.0.
The raw runs are in the Phase 0 spike (`spike.md`, "H2/H1 re-verification"), with the transcript kept
in the task folder.

| Skill | Delegates? | State | Evidence or what is missing |
|---|---|---|---|
| `prime` | no | measured | `pi --provider openrouter --model anthropic/claude-sonnet-4.5 --approve -e worker/pi/kingpin-harness.ts -p "/skill:prime 93"` in a scratch clone: exit 0, Phases 2 to 4 completed, full project and issue context produced. |
| `plan` | no | unmeasured | Needs a spawned or hand-driven worker with a plan request; no run yet. |

The fleet-level end-to-end (a spawned pi worker on a real issue, followed by `kingpin wait`, a
mid-run `kingpin send`, `kingpin land` and `kingpin done`) is not covered by the table either: it
needs an orchestrator session. `measured` above means the skill itself ran to completion on Pi; it
does not mean the fleet drove it.

Kingpin-injected worktree configuration files (`.agents/rules/kingpin.md`, `.agents/hooks.json`, `.opencode/opencode.json`, the historical `.opencode/config.json` described below, `.opencode/plugins/package.json`, `.opencode/plugins/kingpin-stop.js`, and a codex spawn's `.codex/skills/<name>` links) stay out of `git status` in a leased worktree through an exclude file Kingpin owns (`~/.kingpin/tasks/<task-id>/exclude`), which that worktree reads through a worktree-scoped `core.excludesFile` (`lib/exclude.sh`). The file the worktree would otherwise inherit is mirrored into the task's file, because the worktree-scoped setting replaces it; a configured ignore file that exists but cannot be read refuses the spawn instead of dropping your rules without a word. The main checkout's `.git/info/exclude` is your file: a linked worktree shares the common dir, so a spawn that appended to it changed your repository on every task and deleted lines it never wrote, and it never writes it now. The only part of it `kingpin guard install` rewrites is the `# kingpin guard` … `# end kingpin guard` block that it writes for its three main-checkout contract copies: the install rewrites the block on every run, and it adopts a loose copy an older version left in the file instead of adding a second line, so one install silences the warning. It may also append a plain `.claude/settings.local.json` line outside the block, when your project does not already ignore that file. `kingpin spawn` names every Kingpin-shaped line outside that block (a broad `.agents/` or `.opencode/` one, or an unmaintained exact path such as `.agents/hooks.json` or the `.opencode/plugins/*` pair) and leaves it for you to remove; it skips the block. The worktree-scoped setting needs git's `extensions.worktreeConfig` flag, which `kingpin spawn` sets once in the project repository; the flag changes no ignore rule by itself. `kingpin done` removes the pointer, the harness files that spawn injected and the task's exclude file, so a pool slot goes back clean for the next lease. A spawn also examines the slot it leased for the harness files an earlier task's cleanup left behind: an older Kingpin hid those through the main checkout's `.git/info/exclude`, so treehouse could hand the slot out as clean and the files surfaced once that line was removed. It deletes one only when the content proves Kingpin wrote it: the agy Stop hook whose only top-level key is `kingpin`, the agy rules file with Kingpin's `trigger: always_on` frontmatter above the worker preamble, the old OpenCode `.opencode/config.json` whose only keys are `permission` and `instructions` pointing into `$KINGPIN_HOME`, and the OpenCode plugin pair, a package file that is exactly Kingpin's and a stop script carrying Kingpin's hook. Each of those is a shape Kingpin itself writes at that path, so the proof holds whatever harness the earlier task ran; `.opencode/opencode.json` is the exception, because it is your project's config as much as Kingpin's, which is why a spawn merges into it and never deletes it. Any other file at a Kingpin path, and any other untracked file, is left in place and named on stderr, because the slot is a checkout of your repository and a delete is not reversible. If those leftovers have already surfaced, treehouse will not lease the dirty slot, so this sweep never runs on it: `treehouse return --force <path>` cleans the slot and puts it back in the pool. Pi contributes no injected file at all: its extension is loaded from the checkout by absolute path and writes nothing into the worktree, so a pi spawn records no injected path and creates no exclude file. A codex spawn records only its per-skill links, never `.codex/` as a whole, so a project's own skills and settings stay visible. Your own `.agents/` and `.opencode/` files stay visible in `git status`, because no broad line is written for you.

`.gitignore` ignores the whole `.agents/` directory. It holds local working artifacts (plans, implementation reports, reviews, injected rules and issue drafts) that agents write while they work, so nothing under it is tracked, including a PRD: adding one needs `git add -f`, and the lint then fails on it. An ignore rule never untracks a path that is already in the index, so `./tests/lint.sh` fails on any tracked path under `.agents/`; the remedy it prints is `git rm --cached <path>`, which leaves the file on disk and ignored.
